# تكامل الدفع عبر Moyasar

## لماذا الفاتورة المستضافة؟

التكامل يستخدم **Moyasar Invoice API**. الخادم ينشئ فاتورة بالمبلغ المعتمد، ثم يحوّل العميل إلى صفحة `checkout.moyasar.com`. بهذه الطريقة لا تدخل بيانات البطاقة إلى موقع مداد التحايا أو Firebase، وتظل وسائل الدفع المعروضة مرتبطة بما فعّله حساب التاجر في Moyasar.

المراجع الرسمية:

- [نظرة عامة وبيئة الاختبار](https://docs.moyasar.com/)
- [المصادقة والمفاتيح السرية](https://docs.moyasar.com/api/authentication)
- [إنشاء فاتورة](https://docs.moyasar.com/api/invoices/01-create-invoice)
- [جلب فاتورة](https://docs.moyasar.com/api/invoices/04-show-invoice)

## التسلسل الأمني

1. الإدارة تعتمد `pricing` بالهللات و`SAR` وتاريخ صلاحية.
2. `createPaymentSession` يعيد قراءة الطلب ويتحقق من الملكية والعرض والحالة.
3. قفل Firestore ومعرف محاولة مشتق من `requestId` يمنعان التكرار المتزامن.
4. الدالة تنشئ فاتورة بمفتاح `MOYASAR_SECRET_KEY` وترسل URLs للنجاح والرجوع والإشعار.
5. يحفظ الخادم ربطًا مستقلًا بين الفاتورة والطلب والمبلغ والعملة.
6. Callback محمي برمز سري طويل، لكنه لا يثق في بيانات POST؛ يستخدم المعرف لجلب الفاتورة رسميًا من Moyasar.
7. لا تُحدّث الحالة قبل مطابقة الفاتورة والمحاولة والمبلغ والعملة وحالة المزود.
8. صفحة النجاح تستدعي `syncPaymentSession`; قيمة `payment=success` في URL لا تمثل إثباتًا.

## الحالات

| Moyasar                | داخل النظام  | السلوك                                 |
| ---------------------- | ------------ | -------------------------------------- |
| `initiated`            | `pending`    | يمكن استكمال رابط الجلسة الصالح        |
| `on_hold`              | `processing` | انتظار تحقق دون محاولة ثانية           |
| `paid`                 | `paid`       | حفظ مبلغ الدفع ومعرف الفاتورة والعملية |
| `failed` أو `expired`  | `failed`     | يسمح بمحاولة جديدة إذا ظل العرض صالحًا |
| `canceled` أو `voided` | `cancelled`  | يسمح بمحاولة جديدة وفق حالة الطلب      |
| `refunded`             | `refunded`   | تسجيل الاسترداد القادم من المزود       |

بدء الاسترداد من لوحة الإدارة ليس منفذًا؛ يتم من لوحة Moyasar حاليًا ثم تزامن حالته. لا تَعِ العميل بمدة وصول الاسترداد، فهي تعتمد على المزود والبنك.

## الأسرار

- `MOYASAR_SECRET_KEY`: للمصادقة مع API من Cloud Functions فقط.
- `MOYASAR_WEBHOOK_TOKEN`: يحمي عنوان Callback غير المصادق عبر Firebase.
- `PUBLIC_SITE_ORIGIN`: أصل صفحة checkout، دون مسار أو query.

لا يحتاج هذا التكامل إلى `pk_test_` في المتصفح لأنه لا يرسم نموذج بطاقة داخل الموقع. لا تضع أي `sk_test_` أو `sk_live_` في JavaScript أو مستودع Git.

## قائمة اختبار قبل Live

- نجاح، فشل، إلغاء، رجوع، انتهاء صلاحية، وإعادة فتح الجلسة.
- Callback مكرر وخارج الترتيب.
- طلبا إنشاء متزامنان بنفس `requestId` وبمعرفين مختلفين.
- تغيير/انتهاء السعر قبل إنشاء الفاتورة.
- اختلاف المبلغ أو العملة أو ربط فاتورة بطلب آخر — يجب أن يرفض.
- منع عميل آخر من إنشاء أو مزامنة جلسة الطلب.
- عدم عرض `paid` من query string أو من حالة محلية.
- سجل التدقيق ووضوح دعم العميل عند فشل الشبكة.
- تأكيد أن بيانات البطاقة تظهر وتُرسل فقط على نطاق Moyasar.

## تشغيل Live

بعد إكمال Sandbox والتحقق من تفعيل وسائل الدفع في حساب التاجر، حدّث `MOYASAR_SECRET_KEY` إلى `sk_live_...` عبر Firebase Secret Manager وأعد نشر الدوال. راقب أخطاء Callback و`paymentReviewRequired` وسجل Moyasar في أول العمليات، واحتفظ بإجراء يدوي موثق للتسوية والاسترداد والدعم.
